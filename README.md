# ЛР4 (підсумкова версія) — одна цілісна програма, а не окремі демонстрації

Головна відмінність від попередньої версії: **весь функціонал ЛР1 + ЛР3 + ЛР4
працює в ОДНОМУ реальному потоці замовлення**. Користувач один раз вводить
дані — і саме на цих даних спрацьовують і перевірки з винятками (ЛР3), і
поліморфна оплата та Strategy-знижка (ЛР4). Нічого не викликається "для
галочки" окремим ізольованим блоком з вигаданими числами.

## Що змінилось порівняно з попередньою версією

**Було:** `Main.java` з ЛР4 демонстрував інтерфейси й Strategy на штучних
прикладах (`order1`, `order2`, `order3`, фіксована сума 739.38), а класи
винятків з ЛР3 (`InvalidDiameterException` і т. д.) лежали поруч, але жодного
разу не викликались — у коді не було жодного `try-catch`.

**Стало:** один наскрізний сценарій:

1. Користувач вводить номер піци, діаметр, кількість — кожне значення
   одразу проходить перевірку (`validateDiameter`, `validateQuantity`,
   `validateTip`), і при помилці кидається саме той виняток з ЛР3, який
   ловиться у `catch`-ланцюжку цього самого `try`.
2. На основі реальних введених даних створюється **один** об'єкт
   `PizzaOrder` зі стратегією знижки `TieredQuantityDiscount`.
3. Якщо клієнт каже, що в нього є промокод — стратегія знижки **реально
   підмінюється** на `PromoCodeDiscount` просто на цьому ж об'єкті
   (`order.setDiscountStrategy(...)`), і чек перераховується.
4. Підсумкова сума (з чайовими) **реально оплачується** одним із трьох
   `PaymentMethod`, який користувач сам обирає (картка / готівка / гаманець).
5. Лише два невеликі бонус-блоки лишились ілюстративними (бо для них
   потрібно кілька замовлень одночасно): сортування масиву замовлень
   (`Comparable`) і демонстрація, що `catch(PizzeriaException)` ловить
   обидва підтипи. Вони виконуються вже ПІСЛЯ основного замовлення,
   не замінюючи його.

## Файли

Жоден допоміжний клас не змінювався — тільки `Main.java` переписаний так,
щоб реально користуватися всіма ними в одному сценарії:

| Файл | Роль |
| --- | --- |
| `Main.java` | **єдиний** сценарій: меню → ввід + валідація → Strategy → оплата |
| `PaymentMethod.java`, `AbstractPaymentMethod.java`, `CardPayment.java`, `CashPayment.java`, `WalletPayment.java` | спосіб оплати (ЛР4, рівень 1-2) |
| `DiscountStrategy.java`, `TieredQuantityDiscount.java`, `NoDiscount.java`, `PromoCodeDiscount.java` | стратегії знижки (ЛР4, рівень 3) |
| `Receiptable.java`, `PizzaOrder.java` | контекст Strategy + два інтерфейси одночасно (ЛР4, рівень 2) |
| `PizzeriaException.java`, `InvalidDiameterException.java`, `InvalidTipException.java`, `InvalidQuantityException.java` | винятки (ЛР3) |

## Компіляція та запуск

```bash
javac *.java
java Main
```

Якщо кирилиця в консолі Windows відображається некоректно:

```bat
chcp 65001
java -Dstdout.encoding=UTF-8 -Dstdin.encoding=UTF-8 Main
```

## Приклад повного сценарію (без помилок)

Ввід: `Іван` → піца `2` → діаметр `35` → кількість `3` → сир `так` →
промокод `так` → `20` → чайові `20.50` → осіб `2` → оплата `1` (картка)

```
Проміжний чек (стандартна знижка за кількістю):
Іван | Пепероні x3 | знижка за кількістю ... | ДО СПЛАТИ:  718.88 грн
Чек після застосування промокоду:
Іван | Пепероні x3 | промокод на 20.0% знижки | ДО СПЛАТИ:  639.00 грн
...
ДО СПЛАТИ З ЧАЙОВИМИ:   659.50 грн
Оплата для Іван через: банківська картка
Знято 659.50 грн з картки **** 4521.
```

Той самий об'єкт `order` і ті самі введені дані — пройшли через валідацію,
Strategy і оплату як один суцільний потік.

## Перевірені сценарії помилок (усі протестовано вручну)

| Що вводить користувач | Виняток | Де в коді |
| --- | --- | --- |
| нечислове значення номера піци | `InputMismatchException` (re-throw з `readInt`) | у `try`, перший `catch` |
| діаметр `33` | `InvalidDiameterException` | `validateDiameter(...)` |
| кількість `0` | `InvalidQuantityException` (checked) | `validateQuantity(...)` |
| чайові `-10` | `InvalidTipException` | `validateTip(...)` |
| осіб `0` | `ArithmeticException` | `quantity / people` |
